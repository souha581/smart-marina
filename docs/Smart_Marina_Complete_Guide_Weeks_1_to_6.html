1. The Big Picture: What is Smart Marina?

In a traditional harbor, marina staff manage docks, boats, electricity, and water manually on paper. Smart Marina is a modern distributed system that automates the entire marina operations:

  • Harbors & Ports (port-service): Tracks marinas (e.g., Port de Sidi Bou Said).
  • Utility Pillars / Bornes (pedestal-service): The physical pedestals on pontoons where yachts connect to power and fresh water.
  • Readings & Usage (consumption-service): Records how many kWh of electricity or m³ of water were consumed.
  • Alerts & Events (notification-service): Notifies staff and sounds alarms when consumption exceeds safety thresholds.
  • Single Entrance (api-gateway): The single reception desk that routes external traffic to the right internal microservice.

Instead of building one large, fragile program (a Monolith), we split the application into Microservices. If one service crashes, all the other services continue running without interruption.

2. Tools & Technologies Explained Simply

What is Spring Boot?

Java by itself requires hundreds of lines of boilerplate setup just to start a web server. Spring Boot provides ready-to-run modules with embedded web servers (Tomcat/Netty). You write your business logic and add simple annotations like @RestController, and Spring Boot handles the HTTP endpoints, JSON parsing, and database transactions automatically.

What is Docker & What is Inside It?

Docker runs applications inside isolated units called Containers. Instead of installing PostgreSQL databases and Kafka directly on your Windows OS (which causes registry conflicts and port clashes), Docker packages each tool in a lightweight, self-contained environment.

Inside your infra/docker-compose.yml, you have 4 distinct containers running:

Container Name Host Port Role Why Separate?
postgres-port 5433 Stores port data (portdb) Owned exclusively by port-service
postgres-pedestal 5434 Stores pedestal data (pedestaldb) Owned exclusively by pedestal-service
postgres-consumption 5435 Stores consumption readings (consumptiondb) Owned exclusively by consumption-service
kafka 9092 Apache Kafka Message Broker Buffers and delivers asynchronous events
Golden Microservice Rule: Database per Service
Each microservice owns its private database. A service is never allowed to directly query or write to another service's database. If pedestal-service needs port info, it must ask port-service through an API call.

What is Postman?

Because backend microservices return raw JSON rather than visual HTML pages, Postman acts as the client. It allows you to simulate requests (GET, POST, PUT, DELETE), inspect status codes (200 OK, 201 Created, 400 Bad Request, 503 Service Unavailable), and verify response headers (such as X-Gateway).

What is Apache Kafka?

Kafka is an asynchronous, distributed message broker. Think of it as a reliable central post office:

  • Producer (consumption-service): Drops a letter into the mailbox: "Pedestal #3 recorded 75 kWh" and immediately returns to work.
  • Topic (consumption-events): The specific mail category where these letters are stored.
  • Consumer (notification-service): Reads the letters from the mailbox and processes alerts.

4. Inside Each Service: The 5 Layers

Every Spring Boot microservice is constructed with the same 5 standard clean layers:

  1. Entity (e.g. Port.java): The Java class that maps directly to the database table.
  2. DTO (e.g. PortRequest.java): Data Transfer Object. Acts as a validator and security layer for input and output data.
  3. Repository (e.g. PortRepository.java): Talks to PostgreSQL. Spring Data JPA generates SQL automatically.
  4. Service (e.g. PortService.java): The business logic layer (verifying uniqueness, applying business calculations).
  5. Controller (e.g. PortController.java): The HTTP interface exposing endpoints (GET, POST, etc.).
  6. Client (e.g. PortClient.java): Uses RestClient to make synchronous HTTP calls to other microservices.

6. Synchronous vs Asynchronous Communication

Feature Synchronous (REST / HTTP) Asynchronous (Kafka / Events)
Metaphor Phone call (both parties must be available) Postal mailbox (drop note, recipient reads later)
In Smart Marina pedestal-service calls port-service consumption-service announces reading to Kafka
Target Service Down? Call fails immediately (503 error) Message stored safely in Kafka; read upon restart
Coupling Tight temporal and spatial coupling Loose coupling (producer does not know consumer)
The Golden Rule Use when you need the response to continue Use when you only need to announce a fact

7. Defense Preparation: Top Questions & Answers

Q1: Why use microservices instead of a single monolith?
A: Fault isolation (if notifications fail, ports and pedestals stay operational), independent database scaling, and modular development across teams.
Q2: Why does every microservice need its own database?
A: To ensure loose coupling. If services shared tables, a schema change or a database crash in one service would bring down all others.
Q3: What is the purpose of the API Gateway, and what must it never do?
A: It provides a single entry point for clients, routing requests to the appropriate service and handling global headers. It must never contain business logic.
Q4: Why use pedestalId as the Kafka message key?
A: Kafka guarantees ordering only within a single partition. Using pedestalId as the key ensures that all readings from the same pedestal arrive in strict chronological order.
