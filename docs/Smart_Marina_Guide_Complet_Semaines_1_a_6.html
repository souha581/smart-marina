🛥️ SMART MARINA — Guide Complet du Projet (Semaines 1 à 6)

Module : Atelier SOA & Microservices | Auteur : Projet Smart Marina | Technologies : Spring Boot, Docker, PostgreSQL, API Gateway, Apache Kafka

Objectif de ce document :
Expliquer de façon simple et accessible tout ce qui a été réalisé de la semaine 1 à la semaine 6 : le rôle de chaque composant, les outils utilisés (Docker, Postman, Spring Boot, Kafka), l'architecture et les questions types pour la soutenance.

1. La Vue d'Ensemble : C'est quoi Smart Marina ?

Dans un port de plaisance traditionnel, la gestion des bateaux, des quais, de l'électricité et de l'eau se fait souvent sur papier. Smart Marina est un système distribué moderne qui automatise toute la gestion du port :

  • Gestion des Ports (port-service) : Enregistre les ports maritimes (ex. : Port de Sidi Bou Said).
  • Gestion des Bornes (pedestal-service) : Gère les bornes physiques sur les pontons où les bateaux se branchent.
  • Gestion des Consommations (consumption-service) : Enregistre les consommations d'électricité (kWh) et d'eau (m³).
  • Gestion des Alertes (notification-service) : Écoute en temps réel et avertit dès qu'un seuil critique est dépassé.
  • Porte d'Entrée Unique (api-gateway) : Reçoit toutes les requêtes extérieures et les achemine vers le bon microservice.

Au lieu de créer un seul gros programme géant (appelé Monolithe), nous avons découpé l'application en Microservices indépendants. Si un microservice tombe en panne, tous les autres continuent de fonctionner sans problème.

2. Les Outils Expliqués Simplement

C'est quoi Spring Boot ?

Java tout seul nécessite des centaines de lignes de configuration juste pour lancer un serveur web. Spring Boot fournit des "briques Lego prémontées" avec un serveur web intégré (Tomcat ou Netty). Il suffit d'ajouter quelques annotations comme @RestController ou @Service pour que Spring gère la base de données, les routes web et le format JSON automatiquement.

C'est quoi Docker & Qu'est-ce qui tourne dedans ?

Docker permet d'exécuter des logiciels dans des boîtes fermées et isolées appelées Conteneurs. Cela évite d'installer manuellement 3 bases de données PostgreSQL et un serveur Kafka sur Windows, ce qui créerait des conflits de ports et ralentirait l'ordinateur.

Dans votre fichier infra/docker-compose.yml, vous avez 4 conteneurs actifs dans Docker Desktop :

Nom du Conteneur Port sur votre PC Rôle Pourquoi est-il séparé ?
postgres-port 5433 Base de données des ports (portdb) Propriété exclusive de port-service
postgres-pedestal 5434 Base de données des bornes (pedestaldb) Propriété exclusive de pedestal-service
postgres-consumption 5435 Base des relevés (consumptiondb) Propriété exclusive de consumption-service
kafka 9092 Courtier de messages Apache Kafka Transmet les événements asynchrones
Règle d'or de l'architecture Microservices : "Une base de données par service"
Chaque microservice possède sa propre base. Un microservice n'a jamais le droit de lire ou d'écrire directement dans la base d'un autre microservice ! Pour obtenir une information, il doit toujours passer par une requête d'API ou un événement.

C'est quoi Postman ?

Comme notre système n'a pas encore d'interface graphique (boutons, pages web), il ne communique qu'en données brutes (JSON). Postman est notre client de test. Il permet d'envoyer des requêtes HTTP (GET pour lire, POST pour créer, PUT pour modifier, DELETE pour supprimer) et de vérifier les codes de réponse (200 OK, 201 Created, 400 Bad Request, 503 Service Unavailable).

C'est quoi Apache Kafka ?

Kafka est un système de messagerie asynchrone ultra-rapide. On peut le comparer à un tableau d'affichage ou une boîte aux lettres de capitainerie :

  • Le Producteur (consumption-service) : Dépose une annonce : "La borne #3 a consommé 75 kWh" et continue son travail immédiatement sans attendre.
  • Le Sujet / Topic (consumption-events) : La catégorie du tableau où cette annonce est épinglée.
  • Le Consommateur (notification-service) : Lit l'annonce et déclenche une alerte si la valeur est anormale.

4. Les 5 Couches d'un Microservice Spring Boot

Chacun de vos microservices est structuré avec rigueur selon les standards industriels :

  1. Entité (Entity, ex. Port.java) : Représente directement la table dans PostgreSQL. Ses attributs correspondent aux colonnes de la table.
  2. DTO (Data Transfer Object, ex. PortRequest.java) : Le garde du corps. Il contrôle et valide les données qui entrent et sortent avec des règles strictes (@NotBlank, @NotNull, @Positive).
  3. Dépôt (Repository, ex. PortRepository.java) : Communique avec PostgreSQL. Grâce à Spring Data JPA, les requêtes SQL sont créées automatiquement sans écrire une seule ligne de SQL !
  4. Service (Service, ex. PortService.java) : Le cerveau du microservice. Il contient la logique métier (vérifier les doublons, appliquer les règles).
  5. Contrôleur (Controller, ex. PortController.java) : La réceptionniste. Il écoute les requêtes HTTP (@GetMapping, @PostMapping) et renvoie les réponses en JSON.
  6. Client (Client, ex. PortClient.java) : Le téléphone du microservice. Utilise RestClient pour appeler un autre service en HTTP.

6. Synchrone vs Asynchrone : La Règle d'Or

Critère Synchrone (REST / HTTP) Asynchrone (Kafka / Événements)
Métaphore Appel téléphonique (les deux doivent être là) Courrier postal (déposé dans la boîte, lu plus tard)
Exemple Smart Marina pedestal-service appelle port-service consumption-service annonce un relevé à Kafka
Si le destinataire est en panne L'appel échoue immédiatement (Erreur 503) Le message attend dans Kafka et sera lu au redémarrage
Couplage Fort (doit connaître l'adresse IP et le port) Lâche (le producteur ignore qui écoute le sujet)
La Règle d'Or À utiliser quand on a besoin de la réponse pour continuer À utiliser quand on doit seulement annoncer qu'un fait s'est produit

7. Préparation à la Soutenance : Questions & Réponses Types

Q1 : Pourquoi utiliser une architecture microservices au lieu d'un monolithe ?
Réponse : Pour l'isolation des pannes (si le service de notification plante, les ports et les bornes continuent de marcher), pour l'indépendance de déploiement et de montée en charge (scaler un seul service très sollicité sans dupliquer tout le système).
Q2 : Pourquoi chaque microservice a-t-il sa propre base de données ?
Réponse : C'est le principe du "Database-per-Service". Cela garantit un couplage faible. Si les services partageaient une base unique, une modification de table par une équipe pourrait casser les autres services, et une panne de la base paralyserait tout le port.
Q3 : Quel est le rôle de l'API Gateway et que ne doit-elle SURTOUT PAS faire ?
Réponse : Elle sert de porte d'entrée unique pour tous les clients externes, gère le routage et la sécurité centrale. Elle ne doit jamais contenir de logique métier (calculs, règles de gestion), qui doit rester dans les microservices.
Q4 : Pourquoi avoir choisi pedestalId comme clé de partitionnement Kafka ?
Réponse : Kafka garantit l'ordre des messages uniquement à l'intérieur d'une partition. En utilisant l'identifiant de la borne comme clé, tous les relevés d'une même borne sont garantis d'être traités dans l'ordre chronologique exact.
